# L3 · 能力提升

## 定位

**学完就能做基础的数字 IC 设计工作。** 内容更专业、更全面，实践项目包含**对接工作**。

到了这一级，重点已经不是"写 Verilog"了——L2 结束时你**会写**了。L3 补的是**会写 RTL 和能承担设计任务之间的差距**：设计流程、时序约束、检查工具、验证方法学、交付规范，以及**怎么和上下游团队配合**。

## 适合谁

- 已经能独立写可综合 RTL（或已完成 L2）
- 目标是入职数字 IC 设计岗 / 转岗 / 在现有岗位上承担实际设计任务
- 需要从"自己写代码"过渡到"在团队里交付模块"

**这一点很重要，不能含糊。** 仓库自带的只有 **iverilog + GTKWave**（其余按需装，见下），它不是工业设计工具链：

| 内容 | 本仓库能做到 | 做不到 |

| RTL 功能设计 | ✅ 完整（iverilog 仿真 + 自动判定） | — |
| 测试台与验证 | ✅ 完整（自检测试台、随机激励、覆盖率概念），功能覆盖率的**合并**能跑（`tools/cov.py`，零下载） | UVM 类库、商业仿真器特性；**代码覆盖率（行/翻转）跑不了**——verilator + mingw 都装了，但 verilator 的 C++ 链路本仓库还没接（缺 MAKE / PYTHON3 / 链接三关），所以 `cov.code` 仍是缺口 |

| Lint / CDC 检查 | ⚠️ 自带 `_lint.py` 只覆盖锁存器；**verilator 已接入**（`tools/_vlint.py`）可补真 lint（位宽/组合环/多驱动）；⚠️ **verible 装是装在（0.0-4296），但还没有调用它的代码**，编码规范检查**目前跑不了** | ❌ CDC 没有成熟开源工具，只能人工审查 + 形式验证辅助 |

**装不装由你定，缺工具不阻塞开课。** 跑 `python tools/check_tools.py --level L3` 看这一级缺什么、缺了会怎样、装什么能补，然后 `python tools/setup_tools.py --install <id> --lock` 装到仓库里（不影响系统环境）。想一次装成跟作者一样，用 `python tools/setup_tools.py --restore-lock`——它照 `tools/tools.lock.json` 装，并**顺带告诉你锁盖不到哪里**（`iverilog` 不在那把锁里，它由 `setup_toolchain.py` 单独装、单独钉版本）。

**注意 `verilator` 分两条路，成本差很多**：`--lint-only` 装完即用；`--binary`（真正编译仿真模型，覆盖率、并发断言靠它）需要 C++ 编译器 + `make`。别把「装了 verilator」当成「断言能跑了」。

⚠️ **这条链的瓶颈是编译器，不是 make** —— 这句**只对了一半**，2026-09-29 换完编译器之后更正的。先说前半：make 那步确实可以用 `mingw32-make` 顶替（verilator 认 `MAKE` 环境变量）。当时本机唯一的 g++ 是 Qt 自带的 mingw 7.3（2017 年），而 verilator 是按 **GCC 15.2.1** 配的，连撞四个坑：`-fcf-protection=none` 不认、`verilated.mk` 里 `python3` 找不到、`GetProcessMemoryInfo` 缺 `-lpsapi`、链接报 `WinMain` 未定义。于是装了现代 mingw-w64（`mingw` 条目）。

**换完之后实测：仍然打不通。** 那个包装完 `found=True` 且 `usable=True`（自检真编过了），但 verilator `--binary` 走到底还是三关：

1. `make` 找不到 → 指 `MAKE` 到 `mingw32-make.exe`，**这关能过**；
2. `verilated.mk` 里 `PYTHON3 = python3` 是**硬编码**、会盖掉环境变量，而 PATH 上那个 `python3` 是 Windows 商店的占位桩（退出码 49）——得用 make 命令行变量才顶得过去；
3. 过了前两关，所有 `.cpp` 都编得出来，**最后卡在链接**：`undefined reference to WinMain` + 一串 `std::__cxx11::basic_string<...>::basic_string(...&&)`。

**这三关本仓库一行代码都没写**，所以 `cov.code`（覆盖率）和 `sva.assert`（并发断言）现在**装齐软件也不能动手**——这也是为什么这两条的 `gap` 是 `software+code` 而不是 `software`：标成 `software` 的话，软件一装它们就被判成「可用」，而实际跑不出来。**`mingw` 是清单里性价比最差的一项**：下 261 MB、占 940 MB 磁盘，换来的是「有一个现代 g++」（这一条是真拿到了），覆盖率/断言那两条一点没动。

⚠️ **OSS CAD Suite 只装整包，不要装分组件**（2026-09-28 实测的分组件，2026-09-29 被整包推翻）。分组件 Windows 资产**不自包含**：`windows-x64-yosys.tgz` 装完，`yosys.exe` 启动即 `STATUS_DLL_NOT_FOUND`——它要 `libgcc_s_seh-1 / libwinpthread-1 / libstdc++-6 / libffi-8 / libreadline8 / tcl86 / zlib1` 一整组运行时 DLL，而组件里一个都不带。表现是**一个字节输出都没有、也没有报错信息**，只看「文件在不在」必然误判成装好了。

根因不是"缺几个 DLL、补上就行"：整包与分组件带的 `libstdc++-6.dll` 存在 **C 库 ABI 分裂**（`std::fpos<int>` vs `std::fpos<_Mbstatet>`），拿 bleyer iverilog 的同名 DLL 顶上只会把 `STATUS_DLL_NOT_FOUND (0xC0000135)` 换成 `STATUS_ENTRYPOINT_NOT_FOUND (0xC0000139)`，**不能混用**。所以清单里 **8 个条目**（yosys / verilator / formal(sby) / eqy / z3 / slang / oss-utils / oss-system-resources）现在统一指向**同一个整包**，`setup_tools.py` 按 `(repo, tag, asset)` 判重，只下一次、只解一次。**不共这个整包的是 `verible`（6.9 MB 独立 zip → `.tools/verible`）和 `mingw`（261 MB zip → `.tools/mingw`，解开后 940 MB）**。

整包（572 MB）**已实测全部能用**：`yosys 0.69+154`、`verilator_bin 5.053`、`z3 4.15.5`、`sby` / `eqy` / `slang 11.0.448` / `gtkwave 4.0.0` 逐一起得来，形式验证真跑通了一个 k-induction 作业。代价是 `.tools/oss` 占 **2.1 GB**。`check_tools.py` 的判据是 `found and usable`（真跑一次功能自检），所以「文件在」不会被当成「能用」。

**所以 L3 的教法会明确区分两类内容**：

- **能动手验证的**：RTL 设计、功能验证、协议实现、CDC 的行为验证 → 照常在仓库里写代码跑判定；综合与结构 lint 走 iverilog 自带的 `-t blif` / `-t sizer` 和 verilator 的 `--lint-only`（**都已接入**，零下载或装完即用）
- **只能讲 + 读 + 手算的**：STA、DFT、低功耗、CDC 静态检查 → 讲清楚原理、给出真实报告样例读解、手算 slack，并在 `progress/notes/` 里留下笔记。**这些内容的检验方式是想明白、说清楚，不是跑通。**
- **软件就位但仓库还没接入的**（暂按「讲」对待，接入后可升级为动手）：verible 驱动的编码规范检查、sby/eqy 驱动的形式验证、`abc -liberty` 驱动的延时估算 → **讲课前先确认接入代码写没写**，没写就说「这个还没接入，我讲原理 + 给你命令自己跑」，**不能说「仓库里跑通了」**
  - ⚠️ **yosys 驱动的面积/编码对比已经不在这一档了**（2026-09-29 接入，见上）——别再把它列进「还没接入」里。反过来的风险更大：把已接入的说成没接入，学习者会去手敲命令行，而仓库里明明有条更稳的路

**L3-18 的 SVA 已按实测改写**，不再指望装工具解决。可用的部分比想象中多，不能用的那部分也有确定的替代（实测结论）：

| 写法 | iverilog 实测结果 |
|---|---|
| `assert property` + `property` / `\|->` | ❌ 语法错误（iverilog，带 `-g2012` 也是）；verilator 只覆盖子集，且要编译出模型才跑得起来，而那条链卡在编译器上（见上） |
| **立即断言** `assert (expr) else $error(...)` | ✅ 可用（`sim.py` 本来就传 `-g2012`），但 `$error` **不改变判定结果**，只打印 |
| `$fatal` | ⚠️ 能停仿真且 `vvp` 退出码为 1，但会在 `TEST_DONE` 之前中断 → `sim.py` 判成 **`inconclusive`**（"没有收尾标记"），不是 `fail` |
| **独立 `always` 块当并发断言，用 `VLEARN_CHECK` 上报** | ✅ 走仓库现成的判定协议，给出**带用例名和时间点的逐条 pass/fail**——这才是本仓库里"写断言"的正确姿势 |

所以这一讲教的是**断言的思想**（前置条件、时序蕴含、`disable iff` 式的豁免窗口），实现手段是手写检查块，判定走仓库协议。学不到的是 SVA 的语法本身——这一点会明说，不含糊。

不含糊其辞是这一级的基本要求——**知道某个东西自己没真正验证过，比假装验证过强得多**。

| L3-32 | **与规格/系统团队对接**：需求变更、规格歧义怎么澄清、变更如何影响 RTL | 写一份规格澄清问题清单 |
| L3-33 | **代码评审（Code Review）**：怎么提意见、怎么接受意见、评审清单 | 评审一份真实 RTL 并写评审意见 |
| L3-34 | 设计文档写作：微架构文档、接口文档、变更记录 | 为自己的项目写完整文档 |
| **综合④** | **本模块综合题：模拟一次完整的模块交接** | 交付 checklist + 交接说明 + 寄存器手册 + 变更记录，然后**接受一次评审**（我扮演 DV/PD/软件三方问问题） | **产出完整的交付文档包**，且能答上三方的问题 |

### 综合题总览

| 位置 | 编号 | 综合题 | 跨哪些讲 | 产出物 |
|---|---|---|---|---|
| 模块 A 末 | 综合① | 完整设计审查 | L3-01~15 | 审查报告 |
| 模块 B 末 | 综合② | 完整验证计划并执行 | L3-16~20 | 覆盖率报告 + 缺陷清单 |
| 模块 C 末 | 综合③ | 多时钟域数据搬运系统 | L3-21~26 | 可验证的 RTL + CDC 风险清单 |
| 模块 D 末 | 综合④ | 模拟完整模块交接 | L3-27~34 | 完整交付文档包 |
| **级别末** | L3-35~40 | 六个实践项目，L3-40 是收尾 | 跨全级 | 项目 + 交付物 |

> **L3 的综合题产出物是"文档 + 代码"，不只是代码。** 这正是 L3 与 L1/L2 最大的区别——模块 A~D 的综合题，一半的分数在文档上。

> **L3-40 是本级的收尾**：把一个模块**从头到尾走一遍真实交付流程**，包括写文档、过 lint、准备交接材料、接受评审。做完这个，才算"能做基础的数字 IC 设计工作"。

## 学完的检验标准

1. 拿到一份规格，能独立完成微架构设计并说明取舍理由
2. 写完 RTL 后能自己判断：综合出来大概多大、关键路径在哪、有没有 CDC 风险
3. 能读懂综合报告和时序报告，知道违例该从 RTL 还是约束上修
4. 能写出让验证工程师和软件工程师**看得懂、用得上**的交付文档
5. 能参与 code review，提得出有依据的意见，也接得住别人对自己代码的意见
6. **清楚知道自己哪些结论是验证过的、哪些是推导出来的** —— 这条最重要

## 学完去哪

去做真实项目。这一级之后，本仓库能提供的系统性内容就到头了——剩下的靠实际项目。如果后续需要补，可以按需回到 `progress/notes/` 里补专题。

## 级别内的摸底

L3 摸底重点在**真实设计经验**和**流程认知**：

- 独立设计过模块吗？从规格到 RTL 完整走过一遍？
- 知道综合是怎么做的吗？见过综合报告或时序报告吗？
- 知道 setup / hold 违例的区别吗？会算 slack 吗？
- 跨时钟域有哪些处理方式？
- 参与过 code review 吗？给别人的 RTL 提过意见吗？
- 和验证/后端/测试团队打过交道吗？

按摸底结果跳模块。如果技术很扎实、只缺流程和对接认知，可以只做模块 A 的后半 + 模块 D + 模块 E 的 L3-40。
